# 富江实机执行记录：没有数据时，我自己去找数据的完整步骤
（FPS2 实战全流程复盘——每一步都是真机做过、验证判据写在旁边，新游戏照此顺序跑）

## 第0步 模板先跑起来，拿到"已知正确的骨架"
- 直接用上游 PUBGM 模板的 GNames/GWorld/类过滤框架编译部署，目标游戏进程 attach 成功 = 基址/读内存通道 OK
- 此阶段允许数据全是错的，但**管线必须先通**（能枚举到对象数量>0）

## 第1步 类名考古（敌人是谁）
1. 遍历 UObject 链把类名全部 dump 出来（GNames 解名），按 pawn/character/fighter/bp_ai 关键词 grep 候选前缀
2. 进对局实测：把匹配到的每个前缀分别画小点+打地址日志 → 对局里"点数≈敌人数、死了少一个"的那个前缀 = 敌人pawn类（FPS2: BP_AI_Pawn_A/B_C）
3. 队伍字节定位：同时读多个 pawn 的同一偏移候选（从 +0x400 到 +0x500 步进8），找"己方一个值、敌人们另一个值"且对局中恒定的字节 → 0x4C8
   判据：换局值稳定、队友同值、敌人异值、尸体值会跳（尸体单列）

## 第2步 坐标链考古（人在哪）
1. pawn 起始指针候选：UE4 通用 RootComponent 常见 +0xD0/+0x130/+0x238——逐个试，判据=解出的指针 +0x10~0x20 处能读到 3×float 且量级像世界坐标(1e2~1e6)
2. 拿到 root 位置后核对屏幕：把该坐标直接 W2S 打点，点跟着人走 = 链对了
3. **C2W 探测（本项目最大考古）**：写 probeC2W——对 Mesh 组件从 +0x180 到 +0x230 步进 0x10 逐候选读 FTransform，三重判据过滤：
   - 四元数模长∈[0.85,1.25]（是旋转）
   - scale 每分量∈[0.05,4]（是变换不是垃圾）
   - 平移与 rootPos **逐轴差<400**（是世界坐标不是局部偏移——这条最关键，0x1A0 是局部偏移 t=(0,-90,0)，前两关能过、这关必死）
   候选顺序表 {0x1C0,0x1A0,...}，全对局反复采样：值随人走的=真 C2W（FPS2=0x1C0，报告里 C2W偏移:1c0 出现即锁定）
4. 骨骼数组三连探：Mesh+0x740/0x750/0x758 读 (data,num)，对局中 num 恒 0 = 游戏不填缓存 → 立即放弃真骨骼，切几何伪骨骼（框内按比例画），不再耗版本

## 第3步 相机考古（W2S 的另两条腿）
1. 沿 GameViewport→PlayerCameraManager 链（模板结构+偏移±扫描）找 ViewMatrix[16] 与 FOV：
   - 矩阵判据：正交+最后一行是平移、每帧变化跟转身对应
   - 转身实测：往左转，矩阵某组列符号同步变 = 对；FOV 读值=90/70 等整数附近且开火不变 = 相机不是武器
2. 每次改动把"矩阵哈希"打进调试报告（Matrix调试=xxxx），哈希变了=数据源被动过，肉眼看不出来时先对哈希


## 第3步·补全：dump 只给"头后面偏移"时，ViewMatrix[16] 怎么自己找出来
（FPS2 实况：用户 dump 只给了相机链上的一个锚点偏移，矩阵是现场挖的——步骤如下）
1. **锚点扩窗读取**：从给的偏移起，向后连读 4KB 原始内存块（相机结构字段挤在同一对象里，间距固定）
2. **结构指纹筛选**，对块内每个 16-float 对齐位置跑四判据：
   - 前 12 个 float 分成三组各为模长≈1 的单位向量（旋转三轴）
   - 三轴两两点积≈0（正交）
   - 第 4 个三元组/列 = 平移，且和"相机位置"字段数值一致（差<视高）
   - 全块里同时满足的通常只有 1~2 个候选
3. **行为复核（关键，指纹会撞）**：
   - 向左转身：三轴列的符号变化方向必须跟转身方向一致（反了=行主序/转置问题，W2S 里换索引序即可）
   - 前进：平移分量变化量≈位移量（对不上=挖到的是别的缓存矩阵，比如投影矩阵）
   - 每个候选都打报告（矩阵哈希+相机行），换装实测框跟人不跟帧才算转正
4. **FOV 顺手锚定**：矩阵候选 ±0x100 内找浮点 55~110 区间、开火不变、开镜可能变的值（FPS2 实测开镜不改，FOV 恒 90）
5. **捷径（跨 UE4 游戏通用）**：UE4 相机结构体布局极稳定——ViewLocation/ViewRotation/FOV/ViewMatrix 的**相对间距**在同类间几乎不变。模板 PUBGM 的链(+0x5f58→+0x680→+0x650)先照抄跑一遍，错了再从锚点±0x400 扫；这比盲扫快一个数量级
6. 负结论记录：UE4 常有"两份矩阵缓存"（实时视图 vs 缓存投影），只有一份的平移≈相机世界位置，另一份是死数据——用第3步的"前进复核"区分

## 第4步 掩体数据考古（物理场景在哪）
1. 从 FPhysxSceneManager 链摸三个 Embree 场景根：静态(st)/地形(hf)/动态刚体(dyn)，各数一下几何体数量 → 52/0/61 这种量级就是摸到了
2. 验证法：站墙后看 LineTraceDist 是否给出≈墙距的数；纯平地=1e9
3. 场景更新节流实测：快速跑动时挡你的墙 2~3 秒才进场景（报告时间戳对屏幕位置）→ 滞回参数按这个下限设计
4. 角色刚体污染确认：静止敌人 ray 恒打中 len-34 附近 = 目标自己在 dyn 场景里 → 终点必须留 45 缓冲（这是从数据反推出来的，不是猜的）

## 第5步 交互考古（触摸坐标系）
1. evdev 逐个 /dev/input/event0..11 读，能报 MT 多点且坐标范围=屏幕物理分辨率(0..1080/0..2408)的=游戏TP通道
2. 注入通道 Down(x,y) 空间确认：拿模板锚点默认(650,1500)按住游戏开火键实验——能打出子弹=注入空间=物理竖屏坐标，与 evdev raw 同系，截取键位可零换算直接复用

## 第6步 参数标定（每个现象一行数据）
- 所有探测期写进调试报告（不猜、不问、不截屏）：每版必加 1~3 行新诊断输出（触点=、ray=、C2W偏移=、键位=）
- 用户描述现象 → 对应报告字段验证 → 只改一个变量重编 → 报告回收对比
- "看起来没效果"先查 DrawIo 位串和版本头（用户跑旧版是最常见假故障）

## 通用铁律（换任何游戏都成立）
1. 管线先通，再修数据；数据全通过报告，不通过肉眼
2. 每个偏移必须有**数值判据**（量级/模长/范围）+**行为判据**（跟人不跟帧）双确认才转正
3. 一条链拿不准时打三样东西进报告：候选值、候选哈希、上一级已确认的兄弟值
4. 失败路径也要写文档（HoldingFire=0x632恒0、FOV法开镜废案都是负结论省钱省版本）
5. 版本迭代=单变量实验，一次改多处必炸且无法归因
